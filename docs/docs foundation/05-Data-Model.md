## Purpose

This document defines the authoritative domain and persistence model for Retroverse V2. It specifies entity identity, relationships, lifecycle, provenance, publication revisions, broadcast state, and integrity constraints required by the Product Specification.

The relational model described here is normative. Physical indexes, query plans, and storage optimizations may evolve provided they preserve these entities and invariants.

## Data Principles

1. **One source of truth:** Each authoritative fact has one canonical persisted owner.
2. **Stable identity:** Retroverse identifiers are immutable and never reused.
3. **Explicit relationships:** Relationships are stored as foreign keys or normalized join records, not inferred from labels.
4. **Published history is immutable:** Published Experience and Program revisions never change in place.
5. **Drafts are editable:** Draft state supports iteration before publication.
6. **No destructive history loss:** Referenced and published records are archived, not hard-deleted.
7. **Provenance survives override:** A manual value may supersede imported data without erasing import history.
8. **Public data is a projection:** Public responses expose approved fields derived from canonical records; they are not a second authority.
9. **Canonical time is UTC:** Instants are stored in UTC. Human calendar entities retain their explicit calendar semantics.
10. **AI output is data only after review:** AI-generated suggestions have no authoritative status until accepted by an Operator into a normal field and audit trail.

## Identifier Standard

### Core Entity IDs

Except for Pass Credentials, a core entity ID has this form:

```text
<PREFIX>_<UUIDv7>
```

Example:

```text
RVTR_0197f4a8-7c25-7f3e-9d9b-1ea986fca131
```

Rules:

- The prefix MUST match the approved entity mapping.
- UUID text MUST be lowercase canonical form with hyphens.
- IDs MUST be generated by the application before insertion.
- IDs MUST be globally unique, immutable, opaque to product behavior, and never reused.
- Ordering by UUIDv7 MAY be used for operational convenience but MUST NOT imply product chronology.
- Slugs and external IDs MUST NOT be used as foreign keys in place of Retroverse IDs.

### Pass Credential IDs

A Pass Credential has this form:

```text
RVSN_<26-character Crockford Base32 random value>
```

The random value MUST contain at least 128 bits of cryptographically secure entropy. It MUST NOT embed timestamps, Patron IDs, Pass IDs, Event IDs, permissions, or other decodable product meaning.

When future access workflows are implemented, persistent storage MUST retain only a keyed hash of the credential secret. The full credential may be shown only at issuance or reissuance.

### Slugs

Public entities MAY have a human-readable slug. Slugs:

- are lowercase ASCII with hyphen separators;
- are unique within entity type;
- may change without changing entity identity;
- must retain redirects from prior public slugs;
- must never contain credentials or private data.

## Common Record Fields

Unless explicitly excluded, mutable domain records contain:

| Field | Type | Rule |
|---|---|---|
| `id` | Retroverse ID | Primary key for core entities. |
| `status` | lifecycle enum | `draft`, `published`, or `archived`. |
| `created_at` | UTC instant | Immutable. |
| `updated_at` | UTC instant | Changes on authoritative mutation. |
| `created_by` | Operator ID or system actor | Required for operator-created records. |
| `updated_by` | Operator ID or system actor | Required for authoritative mutation. |
| `lock_version` | integer | Incremented for optimistic concurrency. |

Published revision tables use immutable `published_at` and `published_by` fields instead of mutable lifecycle state.

### Enforced Target Reference Contracts

Tables that must reference one of several domain types use nullable real foreign-key columns plus a database check requiring exactly one non-null target. They MUST NOT use an unenforced `entity_type`/`entity_id` pair.

**Public Target Reference** columns are `artist_id`, `album_id`, `track_id`, `chart_id`, `week_id`, `month_id`, `year_id`, `decade_id`, `era_id`, `experience_id`, and `program_id`. Exactly one is non-null.

**Slug Target Reference** columns are `artist_id`, `album_id`, `track_id`, `chart_id`, `era_id`, `experience_id`, and `program_id`. Exactly one is non-null.

**Temporal Reference** columns are `week_id`, `month_id`, `year_id`, `decade_id`, and `era_id`. Exactly one is non-null. The referenced row is the authoritative period; a separate type discriminator is derived and not stored.

**Temporal Subject Reference** columns are `track_id`, `album_id`, `chart_id`, and `experience_id`. Exactly one is non-null.

**Provenance Target Reference** contains the Public Target Reference columns plus `chart_issue_id`, `chart_entry_id`, `media_asset_id`, and `temporal_relation_id`. Exactly one is non-null.

Immutable Audit Events are the sole exception. They retain a typed identifier value as historical evidence and do not claim a live foreign-key relationship.

### Slug Redirect (`slug_redirect`)

| Field | Type | Rule |
|---|---|---|
| `id` | UUIDv7 | Primary key. |
| `old_slug` | text | Valid normalized prior slug. |
| Slug Target Reference | foreign keys | Exactly one currently canonical target. |
| `created_at` | UTC instant | Immutable. |
| `created_by` | Operator ID | Required. |

Current and historical slugs share one unique namespace within each target entity type. Redirect resolution succeeds only when the target is publicly visible and MUST reject loops or multi-hop chains; changing a slug rewrites prior redirects directly to the canonical target.

### Entity Alias (`entity_alias`)

| Field | Type | Rule |
|---|---|---|
| `id` | UUIDv7 | Primary key. |
| `alias` | text | Normalized matching value. |
| Public Target Reference | foreign keys | Exactly one canonical entity. |
| `source_record_id` | Source Record ID | Optional provenance. |
| `created_at` / `created_by` | instant / Operator ID | Required. |

Aliases support curation and duplicate matching and are not public identities. A merge archives the source identity, adds necessary aliases and slug redirects to the retained identity, and appends one immutable Audit Event naming both identifiers.

## Collection Model

### Artist (`artist`)

| Field | Type | Required | Notes |
|---|---|:---:|---|
| `id` | `RVAR` ID | Yes | Primary key. |
| `name` | text | Yes | Canonical display name. |
| `sort_name` | text | Yes | Search and sorting form. |

An Artist is a person or group credited in relation to a Track or Album. The model does not infer personhood, membership, or legal identity.

### Album (`album`)

| Field | Type | Required | Notes |
|---|---|:---:|---|
| `id` | `RVAL` ID | Yes | Primary key. |
| `title` | text | Yes | Canonical title. |
| `sort_title` | text | Yes | Search and sorting form. |
| `slug` | text | For public visibility | Unique among Albums. |
| `release_date` | date | No | Exact date when known. |
| `release_year_id` | `RVYR` ID | No | Required when only year is known. |
| `image_asset_id` | Media Asset ID | No | Approved cover or representative image. |
| common fields | — | Yes | Lifecycle and audit metadata. |

An Album is one curated release configuration. A materially different title, credited edition, Track membership, or Track order is a separate Album. Format, territory, catalog-number, and remaster variants may share an Album when the curated title, credits, membership, and order are unchanged; their distinct external identifiers remain provenance, not identity.

Operational identity examples: a deluxe edition with added Tracks or a regional edition with different order is a separate Album; vinyl and compact-disc issues with the same curated title, credits, membership, and order may share one Album; a compilation is a separate Album even when every included Track retains its existing Track identity.

| Field | Type | Rule |
|---|---|---|

| `artist_id` | `RVAR` ID | Foreign key. |
| `credit_text` | text | Optional display override. |
| `position` | positive integer | Unique within Album. |

An Album may have multiple credited Artists. An Artist may be credited on multiple Albums.

### Track (`track`)

| Field | Type | Required | Notes |
|---|---|:---:|---|
| `id` | `RVTR` ID | Yes | Primary key. |
| `title` | text | Yes | Canonical title. |
| `sort_title` | text | Yes | Search and sorting form. |
| `slug` | text | For public visibility | Unique among Tracks. |
| `duration_seconds` | positive integer | No | Canonical known track duration. |
| `release_date` | date | No | Exact date when known. |
| `release_year_id` | `RVYR` ID | No | Required when only year is known. |
| `explicit` | boolean | Yes | Defaults to `false`; curator-controlled. |
| `notes` | text | No | Private curator notes. |
| common fields | — | Yes | Lifecycle and audit metadata. |

A Track is one specific recording, mix, edit, live performance, or re-recording. The same recording reused on multiple Albums retains one Track. A materially different performance, mix, or edit receives another Track. A mastering-only change does not create a Track unless the curator lacks sufficient evidence to establish equivalence. Musical compositions and abstract works are not separate Release 1 entities.

Operational identity examples: a radio edit and full-length mix are separate Tracks; a live rendition and studio rendition are separate Tracks; a compilation reuse of the same recording is the same Track; a remaster with no evidenced performance, mix, or edit change is the same Track. Uncertain matches remain separate duplicate candidates until an Operator resolves them.

| Field | Type | Rule |
|---|---|---|

### Era (`era`)

| Field | Type | Rule |
|---|---|---|
| `id` | `RVER` ID | Primary key. |
| `name` | text | Unique formal name. |
| `slug` | text | Unique among Eras. |
| `start_date` | date | Required. |
| `end_date` | date | Optional inclusive end. |
| `description` | text | Curator-approved public definition. |
| common fields | — | Lifecycle and audit metadata. |

Eras are curated historical ranges. They MAY overlap; overlap has no implied hierarchy.

### Temporal Membership

- A Month belongs to exactly one Year.
- A Year belongs to exactly one Decade.
- A Week references the Year whose number is its ISO week-numbering year; this is not a claim that every date in the Week is contained by that Gregorian Year.
- A Week may overlap two Months; month association is derived from dates and is not stored as a single parent.
- An Era may overlap any temporal entity and has no parent unless a later approved model adds one.
- Date overlap is derived only from stored authoritative ranges. Curated context is stored explicitly and MUST NOT be inferred from labels.

### Temporal Relation (`temporal_relation`)

| Field | Type | Rule |
|---|---|---|
| `id` | UUIDv7 | Primary key. |
| Temporal Subject Reference | foreign keys | Exactly one subject. |
| Temporal Reference | foreign keys | Exactly one Week, Month, Year, Decade, or Era. |
| `relation_kind` | enum | `release`, `chart_coverage`, or `curated_context`. |
| `source_record_id` | Source Record ID | Required for imported/derived source facts; optional for manual context. |
| `chart_issue_id` | Chart Issue ID | Required only for `chart_coverage`. |
| `created_at` / `created_by` | instant / Operator or system actor | Required. |

The subject, selected period, and `relation_kind` tuple is unique. A `release` relation is permitted only for a Track or Album and must select a period whose authoritative range contains the known release date; when only a year is known, it may select only that Year or its Decade. `chart_coverage` is permitted only for a Track, must reference the supporting Chart Issue, and must select that issue's Week. `curated_context` requires an Operator or identified import source and records an intentional contextual association rather than a derived date fact. Relations point from subject to period; inverse period-to-subject navigation is a query over the same rows, never a duplicate relationship. Every Time Capsule Track must have a relation to its selected period; the relation is validated before publication. Temporal exploration uses these rows plus direct Month→Year and Year→Decade relationships and documented date-overlap queries.

## Media Model

### Media Asset (`media_asset`)

Media Asset represents an image, audio reference, or video reference. It is a supporting entity with an internal UUIDv7.

| Field | Type | Rule |
|---|---|---|
| `id` | UUIDv7 | Primary key. |
| `kind` | enum | `image`, `audio`, or `video`. |
| `provider` | text | Controlled adapter key. |
| `provider_key` | text | Provider-specific opaque key. |
| `canonical_url` | text | Optional; private configuration may differ from public projection. |
| `mime_type` | text | Optional. |
| `duration_seconds` | positive integer | Required for playable audio/video. |
| `seekable` | boolean | Required for audio/video. |
| `offset_precision_ms` | nonnegative integer | Required when seekable. |
| `browser_playback_status` | enum | `supported`, `visual_only`, or `unsupported`. |
| `width` / `height` | positive integer | Required for images when known. |
| `alt_text` | text | Required for public informational images. |
| `caption` | text | Optional. |
| `eligibility_status` | enum | `pending`, `approved`, `blocked`, `unavailable`. |
| `eligibility_note` | text | Private Operator note. |
| `verified_at` | UTC instant | Optional. |
| `approved_at` / `approved_by` | instant / Operator ID | Required when approved. |
| `approval_basis` | text | Required when approved; Operator-supplied evidence or rationale. |
| `approval_expires_at` | UTC instant | Optional. |
| `revoked_at` / `revoked_by` | instant / Operator ID | Required when an approval is revoked or blocked. |
| `source_record_id` | Source Record ID | Optional provenance. |

`(provider, provider_key)` is unique.

Approval is one global Release 1 Operator assertion until revoked or expired; it is not a legal-rights inference. An expired approval is treated as `pending` until renewed. The public media projection is produced by the Media Adapter only after a current eligibility and capability check. Revocable Media Assets use no shared cache and expose no directly public object URL; provider secrets and private source notes are never part of the public model.

### Track Media Asset (`track_media_asset`)

| Field | Type | Rule |
|---|---|---|
| `track_id` | `RVTR` ID | Foreign key. |
| `media_asset_id` | Media Asset ID | Foreign key to audio or video only. |
| `association_kind` | enum | `canonical`, `alternate`, or `excerpt`. |
| `source_record_id` | Source Record ID | Optional provenance. |
| `created_at` / `created_by` | instant / Operator ID | Required. |

The tuple `(track_id, media_asset_id)` is unique. Experience playable media must match one of these rows for its primary or featured Track.

After a Media Asset is referenced by a published revision, its `kind`, provider identity, provider key, duration, stored-object identity, and capability evidence are immutable; replacing any of them creates a new Media Asset. Eligibility, verification time, approval basis, expiry, and revocation remain mutable safety state and are never copied into an immutable snapshot as a guarantee of current delivery.

### Experience Revision (`experience_revision`)

| Field | Type | Rule |
|---|---|---|
| `id` | UUIDv7 | Primary key. |
| `experience_id` | `RVEX` ID | Required. |
| `revision_number` | positive integer | Unique within Experience. |
| `state` | enum | `draft` or `published`. |
| `headline` | text | Required public headline. |
| `narrative` | text | Optional public narrative. |
| `duration_seconds` | integer 15–900 | Required. |
| `primary_visual_mode` | enum | `image` or `type_layout`; required. |
| `image_asset_id` | Media Asset ID | Required and image-kind when visual mode is `image`; otherwise null. |
| `media_asset_id` | Media Asset ID | Optional approved audio/video only. |
| `media_track_id` | `RVTR` ID | Required when media is present; composite reference to Track Media Asset. |
| `media_start_seconds` | nonnegative integer | Defaults to 0. |
| `media_end_seconds` | positive integer | Optional; must exceed start. |
| `published_at` / `published_by` | instant / Operator ID | Required only when published. |
| `snapshot_schema_version` | positive integer | Required for published revision. |
| `public_snapshot` | JSONB | Required immutable canonical public projection for published revision. |
| `content_hash` | SHA-256 text | Hash contract defined below; required when published. |

Published rows and their type specification, item, and link rows are immutable. At most one draft revision exists per Experience. `type_layout` is a deterministic renderer over the immutable snapshot and type-specific content, so it remains a valid primary visual without an image. The snapshot contains every audience-visible label, credit, relationship, rank, order, visual input, and media metadata needed to reproduce the presentation. Current media eligibility is checked separately and may suppress delivery without changing the snapshot.

Snapshot hashing uses `SHA-256` over UTF-8 bytes of `rv2-public-snapshot:<snapshot_schema_version>\n` followed by the snapshot serialized with the RFC 8785 JSON Canonicalization Scheme. Arrays preserve audience-visible order. The snapshot must not contain floating-point non-finite values, private fields, mutable URLs, eligibility assertions, or values loaded from current identity rows at render time.

## Broadcast Model

### Channel (`channel`)

Release 1 contains one row:

| Field | Value |
|---|---|
| `key` | `channel-zero` |
| `name` | `Channel Zero` |
| `public_path` | `/` |

The key is a stable singleton configuration key, not a new core entity identifier.

### Broadcast State (`broadcast_state`)

| Field | Type | Rule |
|---|---|---|
| `channel_key` | text | Primary key; `channel-zero`. |
| `active_program_revision_id` | Program Revision ID | Required and published. |
| `effective_started_at` | UTC instant | Required. |
| `start_offset_seconds` | nonnegative integer | Less than Program duration. |
| `fallback_program_revision_id` | Program Revision ID | Required and published. |
| `manifest_version` | positive integer | Incremented on state change. |
| `updated_at` | UTC instant | Required. |
| `updated_by` | Operator ID or system actor | Required. |
| `lock_version` | integer | Optimistic concurrency. |

Canonical position at time `t` is:

```text
position = (start_offset_seconds + max(0, t - effective_started_at)) mod program_duration
```

The Program Item whose interval contains `position` is current. There is no persisted per-audience playback position.

`t` is PostgreSQL `statement_timestamp()` obtained in the same read transaction as Broadcast State and Program data. Application-node clocks are not canonical.

### Broadcast Readiness

`is_broadcast_ready(program_revision_id)` is one domain predicate. It returns true only when:

1. the Program revision is published, immutable, non-empty, and within duration/item limits;
2. its Program identity is `published` for new activation or is the already-active archived identity allowed to continue;
3. every referenced Experience revision is published, immutable, and has a valid snapshot and type specification;
4. every referenced identity and required public relationship is resolvable under public-visibility rules;
5. every Experience has one valid primary visual mode;
6. every referenced playable Media Asset is currently approved, unexpired, capability-compatible, and associated with the primary/featured Track; and
7. all stored offsets, durations, and content hashes validate.

Fallback configuration and all new activations require this predicate. A mutation that would make the active or fallback revision unready locks Broadcast State and atomically activates a ready fallback when possible. The reconciliation worker also evaluates the predicate at least every five seconds and uses compare-and-set on `lock_version`; exactly one successful automatic transition appends one Audit Event. Manifest reads never mutate canonical state.

### Channel Manifest

Channel Manifest is a derived public DTO, not a persisted authority. It contains:

- `channelKey`;
- `serverTime`, from the canonical PostgreSQL read transaction;
- `manifestVersion`;
- active Program ID, revision ID, title, and duration;
- current Experience ID, revision ID, type, public content, start and end offsets;
- elapsed seconds within the current Experience;
- next Experience public summary;
- media projection when eligible;
- fallback indicator when active.

## Reserved Event and Access Model

Event (`RVEV`), Venue (`RVVE`), Patron (`RVPT`), Pass (`RVPA`), and Pass Credential (`RVSN`) retain only their reserved identities and glossary meanings in Revision 1. Release 1 defines no tables, fields, relationships, lifecycle, API, route, or runtime behavior for them.

A later approved Product Specification and Data Model must define those schemas before implementation. A future Pass Credential remains an opaque secret and may never be stored in clear text. No Release 1 migration or code may create or depend on reserved access tables.

## Lifecycle and Deletion

### Lifecycle Transitions

```text
draft -> published -> archived
draft -> archived
archived -> draft       (when no immutable publication rule is violated)
archived -> published   (restore of an already published identity, not mutation of revisions)
```

Experience and Program revision state is only `draft` or `published`. A published revision is never changed to draft or deleted.

### Hard Deletion

Hard deletion is allowed only when all are true:

1. the record is a draft or failed staging record;
2. it has never been published;
3. no foreign-key reference exists;
4. no audit, provenance, or compliance requirement requires retention;
5. the Operator confirms the action.

All other removal uses archival state.

## Transactions and Concurrency

The following operations MUST be atomic transactions:

- publishing an Experience revision and updating its identity pointers;
- publishing a Program revision and its ordered items;
- committing an Import Job batch;
- changing Broadcast State and appending its typed Audit Event;
- approving or blocking a Media Asset and appending Audit Event;
- archiving a record and validating reference impact.

Every canonical mutation that requires derived work writes its Outbox Event in the same transaction. Publication calculates the immutable snapshot and content hash before commit; a snapshot/hash mismatch aborts the transaction.

Mutable operator forms use optimistic concurrency through `lock_version`. A stale update returns a conflict and does not overwrite newer data.

Broadcast State updates additionally lock the singleton row for the duration of the transaction.

## Public Data Projection

Public queries may expose only:

- immutable published Experience and Program snapshots that satisfy current visibility rules;
- collection entities that are published or referenced by published content;
- approved public text and imagery;
- approved playable media projection;
- derived relationships required for exploration;
- canonical Channel Manifest.

Public queries must exclude:

- private notes;
- raw provenance payloads;
- source licensing notes not marked public;
- provider credentials or private URLs;
- operator identity details;
- draft revisions;
- import staging data;
- audit snapshots;
- reserved future Patron and Pass data.

Public projection logic belongs in a single application module and is tested as a security boundary. Public visibility is evaluated from canonical rows at request time. Search Documents may rank candidates but cannot grant visibility.

## Derived Data and Caches

The following MAY be derived or cached:

- search documents;
- entity relationship counts;
- non-revocable repository-owned brand image transformations;
- Program cumulative offsets;
- public sitemap data.

Rules:

1. Every derived record identifies its source record or source version.
2. A cache may be discarded and rebuilt without information loss.
3. A cache never accepts authoritative writes.
4. Published revision content hashes detect stale derived output.
5. Broadcast State is never cached as the sole authority.
6. Channel Manifest, revocable Media Asset delivery, and visibility-sensitive entity responses use `no-store` shared-cache policy in Release 1.
7. A derived search or sitemap row is filtered through current canonical visibility at response time.

## Data Decisions and Rationale

The canonical wording and status of each decision are maintained in [RV2-FND-02](./02-Decision-Log.md#incorporated-decision-rationale). This section supplies data-model rationale only.

| Decision ID | Decision | Rationale |
|---|---|---|
| DEC-0031 | Core IDs use entity prefix plus UUIDv7; Pass Credentials use random opaque Base32 secrets. | The format is globally unique, readable by entity type, generation-friendly, and does not use mutable natural keys. Credentials require non-time-ordered cryptographic opacity. |
| DEC-0032 | PostgreSQL is the canonical persistence model, expressed as normalized relational tables, transactional outbox records, leased jobs, and rebuildable search projections. | The domain is relationship-heavy and integrity-sensitive; one transactional authority prevents a second state store and closes commit-to-worker delivery gaps. |
| DEC-0033 | Time uses ISO Weeks, Gregorian Months and Years, fixed ten-year Decades, independently curated Eras, and PostgreSQL statement time as the canonical broadcast clock. | This provides deterministic calendar and runtime semantics while preserving honest overlaps and avoiding application-node clock divergence. |
| DEC-0034 | Published Experience and Program content is immutable, revisioned, and stored as a versioned public snapshot with a canonical content hash. | Snapshotting every audience-visible dependency makes historical presentation reproducible while current media-safety state can still suppress revoked delivery. |
| DEC-0035 | Release 1 persists no audience identity; future Pass Credential storage retains only a keyed hash. | Anonymous access minimizes data collection, and credential hashing preserves opacity if access features are later implemented. |
